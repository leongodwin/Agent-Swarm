# Worker evidence and preflight — Phases 0 and 1

This source change adds native-session evidence and a supported-hook readiness gate. It does not establish live platform readiness, production compliance, correct application of guidance or independent QA acceptance. Demo remains simulated. No target contracts are generated or installed automatically.

## Operational change

Real authoring and QA tasks dispatched by the swarm require `.cubefarm/worker-preflight.json` in their project worktree. The delivery owner must prepare and independently review that contract against actual advertised tools and safe result schemas before enabling work. Missing, oversized, ambiguous or invalid authoring contracts stop native launch before model usage. Existing project files and office state are not migrated or rewritten. Projects without contracts will be blocked on their next real authoring/QA launch; the CEO can still coordinate remediation. Tests use isolated homes and synthetic providers.

Discovery/design mode is assigned by the shared task stage, never by the agent's tool arguments; QA always uses authoring readiness. Without a contract, these stages may perform named local reads and scoped office discovery (`delivery_record` read/finding/inspect_repository plus read-only capability/template tools). Design additionally permits office-owned synthesis/result operations. External platform reads need exact reviewed probes in a contract; `mode: "discovery"` permits such probes without inventing a known target. Existing malformed contracts still block launch. Discovery mode permanently denies shell, authoring and approval, even after its probes pass. Completion is recorded as `discovery-only`, never authoring-ready; record-only discovery is held for independent review/issue disposition without a PR-completion nudge.

The contract is pinned by its bytes at session admission. It contains the installed skill IDs/content hashes, exact read-only MCP calls and scalar assertions over their JSON results (or the narrow native Canvas adapter described below). Every contract must cover the caller identity and target. Add explicit access assertions for each required capability where a safe read exposes them. A safe read does not prove mutation permissions, compilation or a user journey: retain these as separate authoring and acceptance checks. A `readOnly: true` declaration requires operator review; Agent Swarm cannot infer whether an arbitrary provider implementation is safe. For Gemini/OpenCode, declare exact observed bridge names in each probe's optional `nativeNames` object, for example `{"gemini":"mcp_synthetic_inspect","opencode":"synthetic_inspect"}`. These examples are synthetic. Names are never inferred by splitting underscores.

## Explicit reviewed-contract publication

From a source checkout, `node --import tsx scripts/install-worker-preflight.ts <existing-canonical-checkout> <reviewed-candidate-file> <reviewed-sha256>` publishes only the exact independently reviewed bytes. Set SWARM_HOME to the intended office when verifying its installed guidance. The candidate must use actual advertised native tool names, required inputs and result pointers, with explicit targets and current skill hashes. The installer does not discover safety or approve a contract: the supplied hash records the operator's publication decision after independent review.

The installer refuses existing targets and linked checkout/contract directories, validates bounded duplicate-free JSON and current guidance, flushes its private file and publishes without replacement. Authority/path/guidance are checked before and after publication. A failed post-publication check leaves the installed file for explicit inspection; it never deletes a possible successor. Every worker still starts without skill reads or probe observations. Installation grants no tenant, task, runtime or release approval. A contract's scope text is descriptive, not a security sandbox. Install separately into each intended project worktree; no global profile or other project is rewritten.

Native array results cannot currently establish observations. Select actual object-returning probes rather than inventing a wrapper. Indexed assertions within a genuine object may deliberately fail closed if provider ordering changes. Verify the actual native full tool names through worker hook evidence. The GraspAI showcase contract uses only explicit-target connection and site catalogue reads plus caller identity; those do not prove mutation permissions or application readiness.

## Worker sequence

1. Developer and QA tool sets expose both `installed_skills` and `read_skill`. Packaging/deployment/permission vocabulary includes Dataverse guidance. Unmatched selection explicitly instructs broader discovery without a task query.
2. The worker receives the pinned contract in its instructions, avoiding a shell-read prerequisite. It reads each pinned skill through `office.read_skill(id, sha256)`. Agent Swarm verifies the returned content hash; supplied guidance remains unverified tool readiness.
3. The worker invokes the exact reviewed probes through its own native tools. Only correlated post-tool JSON results or exact supported native Canvas replies matching all assertions establish observations. Tool listings, arbitrary textual claims, malformed results, provider errors, uncorrelated results and failed calls do not.
4. Until ready, supported hooks allow only pinned probes, skill discovery/reading and named read-only file diagnostics. Shell execution, authoring and QA approval tools are denied. Existing governance and task authority still apply.
5. Successful observations expire after the configured 30–600 seconds. Failed refreshes revoke previous observations. Changed contract bytes, missing/changed guidance or unreadable configuration deny further work. Resume/restart creates a new gate and requires fresh observations.
6. A native session cannot report successful completion while required readiness is missing. This is not a replacement for the complete QA verification matrix planned for Phase 5.

Guidance is resolved once per task. Each subsequent checkpoint checks pinned file contents, skill configuration and the pinned plugin's selected version directly; it does not rehash the entire installed catalogue. OpenCode sends complete post-tool evidence up to 768 KiB of text and 900 KiB of encoded hook body; larger evidence becomes an explicit failure rather than truncated apparent success. Display summaries remain clipped independently. Readiness and audit classification share bounded result interpretation, including nested JSON error envelopes.

## Native Canvas and FlowAgent worker integration

`installed_skills` now returns `mcpBindings` alongside guidance. Each available binding identifies a versioned installed skill, canonical server name, configuration hash and, where available, native entry hash. These are proposed installation facts, not approval, authenticated access or permission to deploy. Select one binding per required server and include its fields (except `status`) in the reviewed contract's optional `mcpServers` array. Each binding must reference one of that contract's pinned skills and have a corresponding exact native read-only probe. Do not duplicate a server when selecting several skills from the same plugin.

Codex and OpenCode worker admission resolves those bindings from the installed plugin, then attaches `canvas_authoring` and/or `flowagent` directly to the normal task session. The worker receives their actual native tool schemas. No change to the user's global CLI configuration is made. Known duplicate Codex server aliases are disabled only for that child session. FlowAgent uses its absolute installed Node entry while retaining the task checkout as its working directory. On Windows, Canvas uses the office-managed .NET 10 SDK's native `dotnet exec ... dotnet.dll dnx` invocation; it does not try to spawn `dnx.cmd` as an executable. Changed configuration, SDK/entry bytes or pinned guidance block further supported execution. Gemini bindings are refused before model work until its administrator-owned protected profile supports these servers; they are never silently dropped.

For the exact native Canvas `connect` success reply, the adapter exposes `appId`, `environmentId`, `username` (lower case) and `connected: true` to assertions. `list_accounts` exposes `username` and `connected: true` only when exactly one account is marked connected. Canonical probe names are `mcp__canvas_authoring__connect` and `mcp__canvas_authoring__list_accounts`; OpenCode may require explicitly reviewed `nativeNames`. Generic success prose, conflicting structured/error envelopes and ambiguous connected accounts do not grant readiness. Pin both the saved app ID and environment, not merely the maker's account. This adapter observes a session connection; it does not establish successful source sync, write access, compilation, publication or user behaviour.

3. Follow native discovery, source sync, authoring and validation contracts. Retain source, documentation and native receipts in the task artifacts. Distinguish development authoring/publication from an accepted release.
4. Use the existing independent task QA and Git merge process. Package actual Canvas/flow components and connection references into the solution expected by `cubefarm.delivery.json`. Direct standalone publication cannot stand in for that release package.
5. Create and independently approve the pinned release. The existing delivery runner owns deployment leases, build/test, import, activation, native readback, correlated flow checks and independent browser verification. Only its completed, independently reviewed current release establishes pipeline delivery. These worker changes do not add a separate standalone-app release engine or relax recovery/QA requirements.

## Phase 0 evidence

`<SWARM_HOME>/session-evidence/<attempt UUID>.jsonl` retains append-only metadata for native runner attempts, including failed admission, supported pre/post-tool observations and completion. Each append is flushed to disk; failure or the 8 MiB per-attempt limit denies further supported execution and prevents successful completion. Evidence remains outside temporary session configuration directories.

Rows include the attempt ID, agent/runtime/role, task key when supplied, prompt hash, source HEAD when readable, sequence/time, resume status, tool/input/result hashes, denial category, contract hash, observed skill IDs/content hashes, probe IDs and readiness. Raw prompts, arguments, tool bodies and credentials are not retained here. Tool names and skill IDs are metadata. Source HEAD does not imply a clean tree. Skill-reading evidence proves delivery of bytes, not comprehension.

Unknown token counts and unavailable cost are explicitly `null`. Phase 6 adds per-current-prompt OpenCode usage with explicit source and coverage; cumulative status-line cost is excluded from attempt evidence. Codex/Gemini ingestion remains unavailable. See [EXECUTION-EFFICIENCY.md](EXECUTION-EFFICIENCY.md). Native completion success is not independent QA acceptance. Pre-assignment failures before the native runner, manager-typed task correlation and architecture jobs outside that runner are not fully covered by this baseline.

From a source checkout, read a scoped local baseline without contacting a service:

```powershell
node --import tsx scripts/session-evidence-report.ts C:\absolute\isolated-office-home
```

The report counts successes, failures, interrupted/incomplete/unreadable attempts, blocked tool calls and usage availability. It retains failed attempts in its denominator. It does not calculate token savings, production reliability or accepted-slice efficiency. Phase 6 adds a separate coordinator dashboard and durable automatic retry cap. No automatic deletion policy is added; the report refuses more than 10,000 attempt files and operators must preserve/archive evidence deliberately.

## Limits and independent QA

- These are trusted native-hook controls, not filesystem/account isolation. Indirect shell commands after readiness, unhooked tools and already-issued platform requests are not physically contained.
- The contract's scope and read-only safety require review. There is no new cryptographic operator approval service or complete platform permission inference.
- Platforms returning only textual results need a reviewed structured adapter, such as the narrow Canvas adapter above; do not weaken assertions to unblock them. Native runtime tool-name/result-envelope compatibility must be verified for each installed Codex/Gemini/OpenCode version.
- Out-of-band identity/target changes between observations cannot be ruled out solely by the freshness window. Existing project authority/configuration checks still apply.
- Independent QA must validate actual skill reads, tool/result correlation, wrong-identity/target denial, stale/changed guidance, storage failure, restart/retained-session behaviour and valid authoring in an explicitly approved development target. No live platform operations were used for this implementation's local acceptance tests.
